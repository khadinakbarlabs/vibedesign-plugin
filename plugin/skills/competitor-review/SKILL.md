# Competitor review

Apply the [work policy](../design/references/work-policy.md). Gather missing public evidence through [design-research](../design-research/SKILL.md) only when useful and authorized. Competitor review also works with supplied links, screenshots, or exports.

1. Define the shared user task and audience. Select three to five relevant competitors when the user has not supplied a set; explain selection and mark incomplete coverage.
2. Compare the same task and context: entry point, first value, navigation, essential actions, content hierarchy, data entry, error recovery, returning use, accessibility, and mobile adaptation.
3. Mark each observation with source/date and whether it came from a rendered interface, static screenshot, review, or inference. Record app version and locale where known. Never infer hidden navigation, touch targets, or live behavior from promotional images.
4. For every claimed strength or weakness, show the observed pattern, user implication, and evidence. A star rating is context, not proof of design quality.
5. Find a specific underserved task or friction. Recommend transferable principles and an original treatment grounded in this product's constraints. Do not clone branding, protected imagery, proprietary copy, or distinctive layouts.
6. Rank opportunities by user impact, evidence confidence, and implementation effort. Keep these dimensions visible instead of inventing a precise combined score.

Deliver `competitors.md` with a comparable task matrix, sources, observed strengths, friction, uncertainties, and three prioritized opportunities. End with one recommended design direction and an explicit acceptance test. Do not claim a conversion lift without actual experimental evidence.
